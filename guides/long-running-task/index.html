Anbot 长任务：能停、能续、能回滚

长任务真正难的是一次跑几个小时以后，你还知不知道它在干什么、做到哪、失败了从哪接。Anbot 用 X-Ray、检查点、接管与恢复，把这些状态摆在台面上。

本页是 30 篇指南中的 1 篇，基于 Anbot 0.0.1；下面给出 4 个步骤、4 条验收标准、3 个限制。

一句话答案：先把验收标准和禁止操作写清楚，让 Main Bot 拆成带产物的步骤；在破坏性操作前强制检查点；跑偏时暂停、接管、修完再交回。

适合谁

  • 要跑迁移、批量处理、长链研究的人
  • 经常遇到「跑了一半不知道怎么办」的团队
  • 需要把执行过程留证据的负责人

怎么做

  1. 写下目标、验收标准、不能动的目录/分支/账号；把这些作为任务约束，而不是散落在聊天里。
  2. 让 Main Bot 拆成 3–6 个步骤，每步说明输入、产物、检查点位置；没有产物的步骤不算完成。
  3. 在删除、推送、发布、改配置前要求检查点；失败时先看 X-Ray 的当前步骤和最后成功点，再从断点恢复。
  4. 需要自己改时使用接管：确认执行者已停、工作区锁定；改完交回时核对还是同一个 Session 和文件夹。

验收标准

  • 每一步都有可检查的产物或日志
  • 破坏性操作前有检查点
  • 失败后能从断点继续，而不是从头重跑
  • 接管和交回没有丢文件或串工作区

边界与限制

  • 检查点保存的是会话位置和工作区文件，不是外部系统的全部状态
  • 第三方 API、数据库、发布动作仍要单独回滚方案
  • 长任务会消耗更多模型调用和时间

常见问题

检查点能恢复数据库吗？

不能。它保存会话和工作区文件；数据库、云服务需要自己的备份与回滚。

任务卡住时一定要重跑吗？

不一定。先看 X-Ray 的最后成功点，能续跑就续跑；不能续跑再从检查点恢复。
