Anbot · 做一次只读代码审查｜2–3 人小队版

代码审查最容易变成风格争论。先把审查范围锁在 diff 和行为变化，再让 Bot 给证据。 人少时最怕职责重叠；每个 Bot 和每个人都要有唯一交付。

本页是 3,000 个场景页中的 1 个，基于 Anbot 0.0.1；下面给出 5 个步骤、5 条验收标准、4 个限制。

一句话答案：先只读 diff 和测试，按缺陷/风险/测试缺口三类列证据，再由人决定改不改。 在2–3 人小队下，先先按交付分角色，不按聊天窗口分角色，再按验收表逐项确认。

适合谁

  • 要快速过 PR 的维护者
  • 不想让 Agent 直接改仓库的人
  • 需要把审查结论落成清单的团队
  • 两三个人分工协作的小队

怎么做

  1. 把 diff、相关文件和测试命令放进工作区，明确只读边界。
  2. 让 Bot 按「会坏什么、怎么复现、缺哪条测试」输出，不写风格意见。
  3. 人工确认高风险项，把结论写成 PR 评论草稿；合并仍由人做。
  4. 写清谁做 Main Bot、谁做专业 Bot，以及每个交付由谁最终确认。
  5. 群聊只放共享上下文；私聊和草稿不要全量同步，避免噪声。

验收标准

  • 每条问题有文件/行号或复现路径
  • 没有把猜测写成确定缺陷
  • 测试缺口和代码缺陷分开
  • 审查后仓库没有未授权改动
  • 每个交付只有一个最终负责人

边界与限制

  • Anbot 不是静态分析器的替代品
  • 大 diff 需要分块，上下文可能不够
  • 只读边界要靠权限和指令一起约束
  • 人手少，跨领域复核仍然要外部支持

常见问题

能自动改代码吗？

默认只读；需要修改时另开任务并让人审批。

能接 GitHub 吗？

可以按只读方式接，合并和发布保留人工确认。

两个人怎么分 Bot？

一个人管 Main Bot 和验收，另一个人管专业 Bot 和领域判断。
