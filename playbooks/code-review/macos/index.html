Anbot · 做一次只读代码审查｜macOS版

代码审查最容易变成风格争论。先把审查范围锁在 diff 和行为变化，再让 Bot 给证据。 macOS 上先确认文件和权限；不要假设云端一定有副本。

本页是 3,000 个场景页中的 1 个，基于 Anbot 0.0.1；下面给出 5 个步骤、5 条验收标准、4 个限制。

一句话答案：先只读 diff 和测试，按缺陷/风险/测试缺口三类列证据，再由人决定改不改。 在macOS下，先先确认工作区路径、磁盘权限和 Apple 芯片/Intel 包，再按验收表逐项确认。

适合谁

  • 要快速过 PR 的维护者
  • 不想让 Agent 直接改仓库的人
  • 需要把审查结论落成清单的团队
  • 在 Mac 上运行的团队

怎么做

  1. 把 diff、相关文件和测试命令放进工作区，明确只读边界。
  2. 让 Bot 按「会坏什么、怎么复现、缺哪条测试」输出，不写风格意见。
  3. 人工确认高风险项，把结论写成 PR 评论草稿；合并仍由人做。
  4. 安装包按芯片选；首次运行按发布页说明放行。
  5. 文件操作只用本地路径；导出前检查换行和编码。

验收标准

  • 每条问题有文件/行号或复现路径
  • 没有把猜测写成确定缺陷
  • 测试缺口和代码缺陷分开
  • 审查后仓库没有未授权改动
  • 安装包与芯片匹配，任务能在本机复跑

边界与限制

  • Anbot 不是静态分析器的替代品
  • 大 diff 需要分块，上下文可能不够
  • 只读边界要靠权限和指令一起约束
  • 部分 Windows 专属工具/Office 能力可能不同

常见问题

能自动改代码吗？

默认只读；需要修改时另开任务并让人审批。

能接 GitHub 吗？

可以按只读方式接，合并和发布保留人工确认。

Apple 芯片和 Intel 用同一个包吗？

不；发布页有 arm64 和 x64 两个包。
