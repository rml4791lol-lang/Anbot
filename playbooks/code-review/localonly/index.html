Anbot · 做一次只读代码审查｜纯本地数据版

代码审查最容易变成风格争论。先把审查范围锁在 diff 和行为变化，再让 Bot 给证据。 纯本地场景先确认模型和工具都不外传，再谈能力。

本页是 3,000 个场景页中的 1 个，基于 Anbot 0.0.1；下面给出 5 个步骤、5 条验收标准、4 个限制。

一句话答案：先只读 diff 和测试，按缺陷/风险/测试缺口三类列证据，再由人决定改不改。 在纯本地数据下，先先列数据流，关掉会外传内容的连接器，再按验收表逐项确认。

适合谁

  • 要快速过 PR 的维护者
  • 不想让 Agent 直接改仓库的人
  • 需要把审查结论落成清单的团队
  • 数据不能出本机的团队

怎么做

  1. 把 diff、相关文件和测试命令放进工作区，明确只读边界。
  2. 让 Bot 按「会坏什么、怎么复现、缺哪条测试」输出，不写风格意见。
  3. 人工确认高风险项，把结论写成 PR 评论草稿；合并仍由人做。
  4. 模型、检索、日志都留在本机；逐项确认没有外部请求。
  5. 敏感文件先脱敏；本地模型能力不足时明确降级范围。

验收标准

  • 每条问题有文件/行号或复现路径
  • 没有把猜测写成确定缺陷
  • 测试缺口和代码缺陷分开
  • 审查后仓库没有未授权改动
  • 数据流图显示没有外部传输，日志本地保存

边界与限制

  • Anbot 不是静态分析器的替代品
  • 大 diff 需要分块，上下文可能不够
  • 只读边界要靠权限和指令一起约束
  • 本地模型能力和更新速度有限

常见问题

能自动改代码吗？

默认只读；需要修改时另开任务并让人审批。

能接 GitHub 吗？

可以按只读方式接，合并和发布保留人工确认。

能完全离线吗？

取决于模型和工具；先确认哪些步骤需要联网。
