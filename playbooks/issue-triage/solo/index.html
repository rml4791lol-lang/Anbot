Anbot · 把 Issue 分诊成可执行任务｜一人公司版

Issue 列表不等于任务列表；分诊要给出影响范围、复现状态和下一步。 你既是老板也是执行者，最缺的是可复跑和可验收，而不是更多 Bot。

本页是 3,000 个场景页中的 1 个，基于 Anbot 0.0.1；下面给出 5 个步骤、5 条验收标准、4 个限制。

一句话答案：先让 Bot 读 Issue 和仓库上下文，按影响/复现/优先级分组，再人工定负责人。 在一人公司下，先先把 Bot 压到 1–2 个，选一条能独立验收的链路，再按验收表逐项确认。

适合谁

  • 每周要清 Issue 的维护者
  • 被重复 Issue 淹没的小团队
  • 需要把用户反馈转成开发任务的人
  • 一个人负责从输入到交付的从业者

怎么做

  1. 拉取 Issue 标题、正文、标签和关联 PR；先不写评论。
  2. 按「可复现/缺信息/重复/需要设计」四类归档，每条给依据。
  3. 生成分诊草稿和缺失信息清单；负责人和优先级由人确认。
  4. 把输入、输出目录和验收清单写在同一个文件里，避免靠记忆。
  5. 每次只改一个变量；失败时回到上一个检查点，不要同时调模型和流程。

验收标准

  • 每个 Issue 有分诊结论和依据
  • 缺信息的 Issue 有具体追问清单
  • 重复 Issue 指向原始链接
  • 没有自动替人排优先级
  • 一个人能在 30 分钟内复跑并解释结果

边界与限制

  • 不能替代产品优先级判断
  • 标签体系不统一会误分
  • 自动评论要先审
  • 没有第二个人交叉复核，事实性结论要额外抽检

常见问题

能自动关闭 Issue 吗？

不建议；可以先写关闭建议，由人确认。

能读私有仓库吗？

取决于你给的连接器权限；先按最小权限接入。

一个人需要几个 Bot？

先 1 个 Main Bot + 1 个专业 Bot，跑通再加；不要用 Bot 数量掩盖流程问题。
