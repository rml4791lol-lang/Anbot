Anbot · 把 Issue 分诊成可执行任务｜代运营/客户交付版

Issue 列表不等于任务列表；分诊要给出影响范围、复现状态和下一步。 客户交付最怕串数据和串口径；先隔离客户，再复用模板。

本页是 3,000 个场景页中的 1 个，基于 Anbot 0.0.1；下面给出 5 个步骤、5 条验收标准、4 个限制。

一句话答案：先让 Bot 读 Issue 和仓库上下文，按影响/复现/优先级分组，再人工定负责人。 在代运营/客户交付下，先按客户建独立工作区和验收清单，再按验收表逐项确认。

适合谁

  • 每周要清 Issue 的维护者
  • 被重复 Issue 淹没的小团队
  • 需要把用户反馈转成开发任务的人
  • 服务多个客户的代理/外包团队

怎么做

  1. 拉取 Issue 标题、正文、标签和关联 PR；先不写评论。
  2. 按「可复现/缺信息/重复/需要设计」四类归档，每条给依据。
  3. 生成分诊草稿和缺失信息清单；负责人和优先级由人确认。
  4. 每个客户单独目录、单独凭据、单独知识库，不共用上下文。
  5. 交付前用同一套验收复核；客户确认前不发布。

验收标准

  • 每个 Issue 有分诊结论和依据
  • 缺信息的 Issue 有具体追问清单
  • 重复 Issue 指向原始链接
  • 没有自动替人排优先级
  • 客户数据不跨项目混用，交付有客户确认记录

边界与限制

  • 不能替代产品优先级判断
  • 标签体系不统一会误分
  • 自动评论要先审
  • 多客户并行会增加上下文和权限复杂度

常见问题

能自动关闭 Issue 吗？

不建议；可以先写关闭建议，由人确认。

能读私有仓库吗？

取决于你给的连接器权限；先按最小权限接入。

能复用同一个 Bot 吗？

可以复用能力模板，但客户数据和凭据必须隔离。
