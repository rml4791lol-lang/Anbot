Anbot · 把 Issue 分诊成可执行任务｜5–10 人团队版

Issue 列表不等于任务列表；分诊要给出影响范围、复现状态和下一步。 团队开始有交接成本；先把任务板和共享事实统一，再谈自动化。

本页是 3,000 个场景页中的 1 个，基于 Anbot 0.0.1；下面给出 5 个步骤、5 条验收标准、4 个限制。

一句话答案：先让 Bot 读 Issue 和仓库上下文，按影响/复现/优先级分组，再人工定负责人。 在5–10 人团队下，先先建一个共享任务板和一个只读事实区，再按验收表逐项确认。

适合谁

  • 每周要清 Issue 的维护者
  • 被重复 Issue 淹没的小团队
  • 需要把用户反馈转成开发任务的人
  • 五到十人的项目团队

怎么做

  1. 拉取 Issue 标题、正文、标签和关联 PR；先不写评论。
  2. 按「可复现/缺信息/重复/需要设计」四类归档，每条给依据。
  3. 生成分诊草稿和缺失信息清单；负责人和优先级由人确认。
  4. 按角色建 Bot，不按人建；每个人知道哪个 Bot 给自己交付什么。
  5. 每周清理一次 Bot 的失败任务和过期指令，避免越跑越乱。

验收标准

  • 每个 Issue 有分诊结论和依据
  • 缺信息的 Issue 有具体追问清单
  • 重复 Issue 指向原始链接
  • 没有自动替人排优先级
  • 交接不靠私聊，能从任务板和文件恢复

边界与限制

  • 不能替代产品优先级判断
  • 标签体系不统一会误分
  • 自动评论要先审
  • 角色多后协调成本上升，不是 Bot 越多越快

常见问题

能自动关闭 Issue 吗？

不建议；可以先写关闭建议，由人确认。

能读私有仓库吗？

取决于你给的连接器权限；先按最小权限接入。

需要几个专业 Bot？

先 2–3 个高频角色；低频任务用同一个 Bot 切换。
