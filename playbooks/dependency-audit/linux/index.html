Anbot · 审查依赖升级风险｜Linux版

依赖升级不是把版本号改大；先看 breaking change、运行时要求和回滚路径。 Linux 多用于构建和服务；先准备依赖，再谈桌面能力。

本页是 3,000 个场景页中的 1 个，基于 Anbot 0.0.1；下面给出 5 个步骤、5 条验收标准、4 个限制。

一句话答案：先锁定升级范围和锁文件，再读变更日志与上游 Issue，最后用最小环境验证。 在Linux下，先先确认 Node/依赖、权限和是否需要图形界面，再按验收表逐项确认。

适合谁

  • 负责依赖维护的人
  • 被安全告警追着跑的团队
  • 要评估大版本升级的开发
  • 在 Linux 服务器/桌面运行的团队

怎么做

  1. 列出现有版本、目标版本、直接/间接依赖和锁文件变化。
  2. 读 changelog 与迁移指南，标出 breaking change、弃用和运行时要求。
  3. 在分支里做最小验证，记录失败点和回滚命令；不要直接推主分支。
  4. 从源码构建，记录版本和依赖；不要混用系统 Node。
  5. 无图形界面的环境只跑能无头执行的任务，桌面能力另行确认。

验收标准

  • 升级范围能对应到锁文件 diff
  • 每个 breaking change 有处理方案
  • 有可执行的回滚路径
  • 验证结果不是只看 CI 绿灯
  • 构建可复现，任务在目标环境跑通

边界与限制

  • 上游 changelog 可能不完整
  • 间接依赖的运行时影响难完全预判
  • 安全扫描结果需要人工分级
  • 官方没有 Linux 安装包，桌面能力不保证

常见问题

能自动升级所有依赖吗？

不建议；先按风险分批，保留回滚点。

能处理私有包吗？

取决于本机凭据和仓库权限，凭据不要写进指令。

有 Linux 安装包吗？

当前发布页没有；需要从源码构建。
