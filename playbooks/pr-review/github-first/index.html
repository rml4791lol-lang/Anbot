Anbot · 把 PR 拆成审查清单｜GitHub 优先版

PR 很大时，审查者会漏掉发布风险；先把 PR 拆成可逐项确认的清单。 GitHub 优先时先只读接入，写操作走草稿和审批。

本页是 3,000 个场景页中的 1 个，基于 Anbot 0.0.1；下面给出 5 个步骤、5 条验收标准、4 个限制。

一句话答案：先按行为变化、兼容性、测试、发布四组拆清单，再让 Bot 为每组找证据。 在GitHub 优先下，先先接一个仓库只读，再让 Bot 写 Issue/PR 草稿，再按验收表逐项确认。

适合谁

  • 要审大 PR 的维护者
  • 需要给团队定审查口径的人
  • 经常漏发布检查的开发
  • 以 GitHub 为任务/代码真源的团队

怎么做

  1. 读 PR 描述、diff、测试和发布配置，列出受影响面。
  2. 按四组生成检查项：行为、兼容性、测试、发布/回滚。
  3. 每项标「已证实/待确认/不适用」，不要把未看过的项打勾。
  4. Issue/PR 状态以 GitHub 为准；其他表只做视图。
  5. 合并、发布、改权限保留人工审批。

验收标准

  • 四个维度都有结论
  • 高风险项有人负责
  • 不适用项有理由
  • 审查记录能附到 PR
  • 没有双写，草稿能回到具体 Issue/PR

边界与限制

  • 不能替代领域专家判断
  • UI/性能问题需要实际运行
  • 发布配置因项目而异
  • API 限流和私有仓库权限要单独处理

常见问题

能直接批准 PR 吗？

不建议；Anbot 生成审查记录，批准由人做。

能只看 diff 吗？

不够；还要看调用方、测试和发布配置。

能自动合并吗？

不建议；合并和发布保留人工确认。
