Anbot · 把 GitHub 接进 Bot 团队｜Linux版

接 GitHub 的第一原则是最小权限；先只读，再草稿，最后才谈写操作。 Linux 多用于构建和服务；先准备依赖，再谈桌面能力。

本页是 3,000 个场景页中的 1 个，基于 Anbot 0.0.1；下面给出 5 个步骤、5 条验收标准、4 个限制。

一句话答案：先接一个仓库做只读，再让 Bot 生成 Issue/PR 草稿，合并和发布保留人工审批。 在Linux下，先先确认 Node/依赖、权限和是否需要图形界面，再按验收表逐项确认。

适合谁

  • 要让 Bot 处理 Issue/PR 的团队
  • 担心 Agent 改坏仓库的人
  • 需要把研发流程自动化的组织
  • 在 Linux 服务器/桌面运行的团队

怎么做

  1. 用最小权限接一个仓库，先只读 Issue、PR 和代码。
  2. 让 Bot 生成分诊、审查或发布草稿；写操作只写评论/草稿。
  3. 设审批点：合并、发布、改权限必须由人确认。
  4. 从源码构建，记录版本和依赖；不要混用系统 Node。
  5. 无图形界面的环境只跑能无头执行的任务，桌面能力另行确认。

验收标准

  • Bot 只能访问授权仓库
  • 写操作有审批记录
  • 草稿能回到具体 Issue/PR
  • 没有直接推主分支
  • 构建可复现，任务在目标环境跑通

边界与限制

  • GitHub API 限流会影响批量任务
  • 私有仓库权限要单独配置
  • 不能替代代码所有者审查
  • 官方没有 Linux 安装包，桌面能力不保证

常见问题

能自动合并 PR 吗？

不建议；合并和发布保留人工确认。

能接多个组织吗？

可以，但每个组织单独授权。

有 Linux 安装包吗？

当前发布页没有；需要从源码构建。
