Anbot · 把 GitHub 接进 Bot 团队｜企业受控环境版

接 GitHub 的第一原则是最小权限；先只读，再草稿，最后才谈写操作。 企业环境先谈数据出网、权限和日志；功能可以后加。

本页是 3,000 个场景页中的 1 个，基于 Anbot 0.0.1；下面给出 5 个步骤、5 条验收标准、4 个限制。

一句话答案：先接一个仓库做只读，再让 Bot 生成 Issue/PR 草稿，合并和发布保留人工审批。 在企业受控环境下，先先做权限矩阵、数据流和审批点，再做试点，再按验收表逐项确认。

适合谁

  • 要让 Bot 处理 Issue/PR 的团队
  • 担心 Agent 改坏仓库的人
  • 需要把研发流程自动化的组织
  • 有安全/合规/采购流程的组织

怎么做

  1. 用最小权限接一个仓库，先只读 Issue、PR 和代码。
  2. 让 Bot 生成分诊、审查或发布草稿；写操作只写评论/草稿。
  3. 设审批点：合并、发布、改权限必须由人确认。
  4. 把模型服务商、数据出网、日志保留和删除政策写成书面材料。
  5. 先在一个低风险部门试点；高风险动作全部保留人工审批。

验收标准

  • Bot 只能访问授权仓库
  • 写操作有审批记录
  • 草稿能回到具体 Issue/PR
  • 没有直接推主分支
  • 权限矩阵、数据流、审批点、日志保留四项有书面记录

边界与限制

  • GitHub API 限流会影响批量任务
  • 私有仓库权限要单独配置
  • 不能替代代码所有者审查
  • 企业网络和采购流程可能拖慢上线

常见问题

能自动合并 PR 吗？

不建议；合并和发布保留人工确认。

能接多个组织吗？

可以，但每个组织单独授权。

能内网部署吗？

取决于模型和网络；先确认哪些能力必须联网。
