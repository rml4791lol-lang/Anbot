**SuperAgent 那种“自主”不是壳，是四样东西。** 你之前那套装了又停，因为它只等 GitHub issue，你不在 GitHub 的活它看不到。

我现在做的是把行为写进 Bot：

1. **触发不用等你说**：定时（早报/收工/周复盘）+ 看门狗查躺着的任务 + 谁失败谁自己起修复。
2. **失败五步**：复现拿到原文 → 找根因（不许把症状当原因）→ 分级 P0/P1/P2 → 修或先绕 → 同一条命令重跑留证据。没重跑 = 没修。
3. **换路规则**：同一条路失败 2 次必须换方法；换 3 种还不行才升级我。
4. **不许静默**：卡 15 分钟没进展，先写进问题台账再升级。这样你看得到它卡在哪，而不是干等着。
5. **修完多问一句**：这个坑会不会再来一次？会就写进经验，同类第 2 次升级成规则。

协议落盘了：`任务标准规范规则/自愈协议.md`，已经发给工程师、前端、后端、运维四家。

**没有统一。实测：Atlas 顶层 8 个目录，只有 ppt.an520.xin 有 eslint + tsconfig + README。** 其余项目连“怎么跑”都没写。

所以现在说“能接手”是假的——新 Bot 接手只能读代码猜。

**三层统一，别只弄一层：**

1. **全局 6 条**（不可谈判，写进所有 Bot 指令）：TS 优先、不提交密钥、不 force-push main、禁无理由 lint 忽略注释、提交前必须 build、改逻辑必须跑测试贴输出。
2. **每项目一份 CONTRIBUTING.md**：怎么装怎么跑、风格以哪个配置为准、本项目三条特有约定。全局不写风格——每个项目本来就不同。
3. **接手清单五步**：跑起来 → 跑测试 → 找到改哪 → 改 → 回归。

已经派工程师做「接手度审计」了：八个项目逐个真跑 lint/test/build，贴输出；缺 CONTRIBUTING 就建；再落一份全局 6 条。做完他会回表格，那时才敢说“能接手”。
